# Commercial Boundary

## Open Source Core

The public core remains free and open for:

- workflow foundation
- deployment scripts
- validation logic
- Postgres-backed pilot path
- demo experience
- local runtime and docs
- operator education and self-hosted experimentation

The shared core is MIT-licensed. Aethonex does not claim exclusive ownership of the core or restrict use of the public software. Customers retain their data, credentials, and infrastructure; rights to bespoke work and any paid deliverables must be defined in the signed scope.

Prospect Dominion is an independent MIT-licensed project. It does not include or depend on other Aethonex products, and there is no integrated suite implied by this repository.

The free Core is the distribution wedge. It is not the full customer delivery model.

## Current paid path: implementation services

The current paid path is a scoped delivery engagement around the MIT-licensed Core. Customers pay for agreed implementation work, not exclusive access to or a restriction on the Core:

- deployment into a real customer environment
- DNS/TLS configuration
- secret management and environment hardening
- workflow implementation around the customer process
- agreed data source integration and custom tuning
- validation against written acceptance checks
- pilot delivery and handover
- customer-specific governance and approval setup

Support and updates must be separately scoped and agreed; they are not implied by the MIT license or by a one-time implementation engagement.

The specific offer, customer responsibilities, price, payment terms, delivery schedule, support, data handling, and rights to bespoke deliverables must be defined in a signed agreement. No standard price or customer license terms are published here.

See [Commercial Offer](COMMERCIAL_OFFER.md) for the initial bounded scope and acceptance expectations.

## Strategic Priorities

The product boundary is intentionally simple:

1. Keep the useful Core MIT-licensed and independently runnable.
2. Charge for scoped implementation and delivery work, not exclusive Core access.
3. Build separate paid modules only when demand, capability boundaries, and licensing are established.

This boundary keeps the public project useful without implying that a paid edition or integrated product suite already exists.

## Future paid software modules

No proprietary Dominion module or paid self-hosted edition is currently shipped. Potential future modules may include:

- versioned connectors for additional customer-approved sources
- specialized workflow packs
- additional, validated governance patterns

These are future opportunities, not hidden paid features inside the Core. A module must have a defined and tested capability boundary, distribution terms, support policy, and compatibility contract before it is offered for sale. It must not make the MIT Core unusable without purchasing the module.
